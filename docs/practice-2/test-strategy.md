# Тест-стратегия СМП

## 1. Цель и область

Цель тестирования — обоснованно судить о том, что система:
1. принимает **корректное платёжное решение** по каждой транзакции;
2. **корректно отражает последствия** этого решения в состоянии (баланс, счётчики, журнал).

Из этого следует приоритет: ошибка в решении или в учёте денег важнее ошибки в справочных и вспомогательных функциях.

## 2. Подходы

Стратегия **аналитическая**: объём и глубина проверок выводятся из анализа требований и рисков.

- **От требований.** Тест существует, только если проверяет требование. Требования нумеруются в реестре, каждый тест ссылается на ID ([test-design.md](test-design.md)); требование без теста — пробел покрытия.
- **От рисков.** Глубина проверки пропорциональна цене ошибки: решения по деньгам проверяются полно (все ветвления, границы, комбинации), вспомогательные функции — на уровне чек-листов.
- **Чёрный ящик плюс проверка состояния.** Система проверяется через внешние интерфейсы, но оцениваем не только ответ, а и побочные эффекты; при отказе проверяем, что состояние **не** изменилось.
- **Один дефект — один кейс.** В негативном кейсе нарушается ровно одно условие, иначе причину отказа не локализовать. Комбинации нарушений проверяются отдельно.
- **Проектируем один раз — реализуем на самом дешёвом уровне.** Один и тот же класс проверок не дублируется на всех уровнях пирамиды (раздел 4).
- **Управляемые данные.** Нужное состояние готовится явно и не берётся «как получилось»; результат не должен зависеть от прошлых прогонов.
- **Имитация отказов.** Поведение при недоступности зависимостей — часть требований и проверяется намеренно.
- **Автоматизация по зрелости.** Сначала проектируем и проверяем руками, автоматизируем стабильные и часто повторяемые проверки.

## 3. Техники тест-дизайна

Техники применяются последовательно: каждая следующая работает с результатом предыдущей.

| Техника | Для чего | Что даёт |
|---|---|---|
| Классы эквивалентности | Входные поля и состояния с конечным числом «типов» значений | Один представитель на класс вместо перебора; для каждого класса — свой ожидаемый результат |
| Граничные значения | Числовые пороги, сравнения `≤`/`<`, размеры страниц и диапазонов | Три точки на границу: ниже, на границе, выше — ловит ошибки «на единицу» |
| Таблица решений | Логика с несколькими условиями и приоритетом проверок | Полный набор правил; фиксирует, какой результат побеждает при нескольких нарушениях |
| Попарное тестирование (PICT) | Независимые параметры, комбинации которых нельзя перебрать целиком | Компактный набор, где каждая пара значений встречается хотя бы раз |
| Позитив + негатив на требование | Каждое требование реестра | Минимум два кейса: условие выполнено и нарушено |

Классы и границы закрывают случаи «одно значение отклонено, остальные в норме», таблица решений — порядок проверок, PICT — взаимодействие параметров между собой. Покрытие всех пар не доказывает полноту: известные критичные комбинации из реестра рисков добавляются вручную.

## 4. Уровни тестирования

| Уровень | Что проверяет | Почему на этом уровне |
|---|---|---|
| Smoke | Система запущена и выполняет базовую операцию | Быстрый отсев неработоспособного стенда до всех остальных проверок |
| Unit | Ветвления бизнес-логики, границы, алгоритмы | Самый дешёвый способ покрыть комбинаторику без инфраструктуры |
| API / компонентный | Контракты сервисов: коды ответов, валидация, коды отказов | Контракт — граница между компонентами; расхождения с ним видны только здесь |
| Интеграционный | Взаимодействие сервисов между собой, с БД и брокером сообщений | Дефекты согласованности и стыков не видны на unit-уровне |
| E2E | Сквозные бизнес-сценарии по всей цепочке обработки | Подтверждает итоговый результат, но дорог — берёт только ключевые сценарии |
| Нагрузочный smoke | Поведение под конкурентным потоком, метрики времени отклика | Единственный способ проявить гонки и деградацию |

Усилия распределяются по пирамиде: основная масса проверок — на нижних уровнях, E2E — только для ключевых бизнес-сценариев.

## 5. Классы рисков

Приоритеты задают порядок проработки; конкретные риски выводятся из классов при составлении плана и кейсов.

| # | Класс риска | Суть | Приоритет | Как снижаем |
|:-:|---|---|:-:|---|
| R1 | Ошибка бизнес-решения | Деньги проводятся или отклоняются неверно: логика, граница, порядок проверок | Высокий | Классы, границы, таблица решений; проверка всех ветвлений |
| R2 | Рассогласование состояния | Ответ, баланс, счётчики и журнал расходятся между собой | Высокий | Проверка состояния после каждой операции, включая отказ и откат; интеграционные тесты |
| R3 | Конкурентность | Параллельные запросы нарушают инварианты и уникальность идентификаторов | Высокий | Параллельные сценарии на одном объекте; нагрузочный smoke |
| R4 | Отказ зависимостей | Недоступность смежных сервисов даёт неверный итог вместо контролируемого отказа | Средний | Имитация отказов; проверка кода и причины отказа, отсутствия побочных эффектов |
| R5 | Некорректные данные | Невалидные или нетипичные данные проходят в бизнес-логику | Средний | Классы эквивалентности входов; проверка валидации и инвариантов генерации |
| R6 | Расхождение ТЗ и реализации | Требование неоднозначно или реализовано иначе | Средний | Разбор ТЗ до написания тестов; расхождение оформляется дефектом, а не подгоняется под результат |
| R7 | Пробелы покрытия | Часть требований или комбинаций не проверена | Средний | Трассируемость «требование ↔ кейс», попарные наборы, критерии выхода по покрытию |
| R8 | Нестабильность стенда и данных | Падения вызваны окружением или остаточным состоянием, а не дефектом | Низкий | Обязательный smoke перед прогоном; управляемые данные; чистый старт после сбоев |

## 6. Что не тестируем и почему

| Область | Основание |
|---|---|
| Безопасность и соответствие PCI DSS | Тестовая среда, реальных данных держателей карт нет |
| Антифрод, клиринг, взаиморасчёты | Не входят в систему по проектному решению |
| Соответствие ISO 8583 на уровне битовых полей | Формат упрощён до JSON; проверяется соответствие контракту |
| UX, локализация, кросс-браузерность интерфейса | Интерфейс вспомогательный, не влияет на платёжное решение |
| Отказоустойчивость инфраструктуры (БД, сеть) | Требует отдельного стенда; проверяется только деградация на уровне сервисов |
| Стабильные метрики производительности в CI | Раннеры не дают воспроизводимых замеров; нагрузка измеряется локально |

## 7. Данные и окружение

- Данные только синтетические; реальные данные держателей карт не используются.
- Тесты изолированы: каждый сам готовит нужное состояние и не опирается на результаты других.
- Редкие состояния (например, нетипичные статусы) создаются явно, а не ожидаются от генератора данных.
- Окружение воспроизводимо и поднимается одной командой; конкретный состав — в плане.

## 8. Управление дефектами

Баг-репорт содержит: заголовок, шаги, ожидаемый и фактический результат, severity, priority, ссылку на требование и тест-кейс.

| Severity | Критерий |
|---|---|
| Critical | Неверное решение по деньгам или потеря данных; обойти нельзя |
| Major | Нарушено требование ядра, есть обходной путь или ограниченный эффект |
| Minor | Нарушено второстепенное требование, на результат операции не влияет |
| Trivial | Косметика, формулировки |

## 9. Метрики

- покрытие требований кейсами;
- доля выполненных и пройденных кейсов, в том числе по приоритетам;
- покрытие ветвлений бизнес-логики (на unit-уровне);
- число дефектов по severity;
- доля нестабильных тестов;
- для нагрузочного прогона — p50/p95/p99, throughput, error rate.

Целевые значения метрик задаются в плане.
