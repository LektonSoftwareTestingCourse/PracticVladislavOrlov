# Практика 2 — Тест-дизайн: Authorization и Card Management

**Единицы измерения.** Все суммы, лимиты и балансы в документе — в копейках (минимальных единицах валюты), как в API. Исключение явно помечено «₽».

**Приоритеты** кейсов: P1 — решение о деньгах и целостность учёта, P2 — устойчивость и вспомогательная логика, P3 — бонусные и вероятностные проверки. Приоритет блоков — в [тест-плане, §2.1](test-plan.md#21-что-тестируем).

## 2. Классы эквивалентности

### 2.1 Статусы карты (поле `status`)

| Класс эквивалентности | Значение | Ожидаемый результат авторизации | Требование |
|---|---|:---:|:---:|
| Действительный статус | `ACTIVE` | продолжает проверку (далее по алгоритму) | AUTH-4 |
| Неактивная | `INACTIVE` | DECLINED `CARD_INACTIVE` | AUTH-4 |
| Заблокированная | `BLOCKED` | DECLINED `CARD_BLOCKED` | AUTH-5 |
| Истёкшая по статусу | `EXPIRED` | DECLINED `54` | AUTH-6 |
| Удалённая | `DELETED` | не участвует; карта не найдена → `14` | CMS-6 |
| Некорректный статус (мусор) | `XYZ`, пусто | 400 Bad Request при `PATCH`, карта не изменяется | CMS-5 |

### 2.2 Сумма транзакции и состояние счётчиков

Проверки лимитов сравнивают **накопленный расход плюс текущую сумму** с лимитом (ТЗ 04 §4), проверка баланса — только текущую сумму.

| Класс | Условие | Ожидание | Требование |
|---|---|:---:|:---:|
| Нулевая сумма | `amount = 0` | не определено ТЗ (Q3) | AUTH-8..10 |
| Отрицательная сумма | `amount < 0` | не определено ТЗ (Q3) | AUTH-12 |
| В пределах дневного лимита | `daily_amount + amount < dailyLimit` | проверка проходит | AUTH-8 |
| На дневном лимите | `daily_amount + amount = dailyLimit` | проверка проходит (граница включительно) | AUTH-8 |
| Сверх дневного лимита | `daily_amount + amount > dailyLimit` | DECLINED `61` | AUTH-8 |
| В пределах месячного лимита | `monthly_amount + amount < monthlyLimit` | проверка проходит | AUTH-9 |
| На месячном лимите | `monthly_amount + amount = monthlyLimit` | проверка проходит (граница включительно) | AUTH-9 |
| Сверх месячного лимита | `monthly_amount + amount > monthlyLimit` | DECLINED `61` | AUTH-9 |
| Меньше баланса | `amount < availableBalance` | проверка проходит | AUTH-10 |
| Равна балансу | `amount = availableBalance` | проверка проходит (граница включительно) | AUTH-10 |
| Больше баланса | `amount > availableBalance` | DECLINED `51` | AUTH-10 |

### 2.3 Срок действия и прочие входы

| Поле / состояние | Класс | Ожидание | Требование |
|---|---|:---:|:---:|
| `expiryDate` | в будущем (следующий месяц и далее) | проход | AUTH-7 |
| `expiryDate` | текущий месяц | проход (допущение Q2) | AUTH-7 |
| `expiryDate` | в прошлом (прошлый месяц и ранее) | DECLINED `54` | AUTH-7 |
| PAN | существующий / несуществующий / с неверной контрольной цифрой Луна | проход / `14` / валидация | AUTH-3, CMS-8 |
| Bin-lookup | отвечает 200 / отвечает 5xx / недоступен (таймаут, контейнер остановлен) | обогащение / 2 retry, затем fallback / fallback без retry | AUTH-2 |
| CMS | доступна / недоступна при чтении карты / недоступна при `reserve` | проход / `05` / `05`, средства не списаны | AUTH-11 |

## 3. Граничные значения

Таблицы раздела — исполняемые кейсы; отдельно в §5 не повторяются.

### 3.1 Дневной лимит `dailyLimit` (AUTH-8), P1

Проверка: `daily_amount + amount ≤ dailyLimit` — граница **включительная**. `daily_amount` задаётся записью в `limit_usage` за сегодня.

| ID | `daily_amount` | `amount` | `dailyLimit` | Ожидаемый результат |
|---|:--:|:--:|:--:|:---:|
| NP-1 (ниже) | 999 | 1000 | 2000 | APPROVED `00` |
| NP-2 (граница) | 1000 | 1000 | 2000 | APPROVED `00` |
| NP-3 (выше на 1) | 1001 | 1000 | 2000 | DECLINED `61` |
| NP-4 (лимит исчерпан, amount=0) | 2000 | 0 | 2000 | не определено ТЗ (Q3), фиксируется наблюдение |

### 3.2 Месячный лимит `monthlyLimit` (AUTH-9), P1

Проверка: `monthly_amount + amount ≤ monthlyLimit`. Расход прошлых дней месяца — записями в `limit_usage`; `dailyLimit` на карте заведомо больше `amount`. В первый день месяца запись «прошлых дней» невозможна — кейсы выполняются со второго числа.

| ID | `monthly_amount` | `amount` | `monthlyLimit` | Ожидаемый результат |
|---|:--:|:--:|:--:|:---:|
| NB-1 (ниже) | 4999 | 1000 | 6000 | APPROVED `00` |
| NB-2 (граница) | 5000 | 1000 | 6000 | APPROVED `00` |
| NB-3 (выше на 1) | 5001 | 1000 | 6000 | DECLINED `61` |

### 3.3 Баланс `availableBalance` (AUTH-10), P1

Лимиты на карте заведомо больше `amount`, `limit_usage` пуст.

| ID | `availableBalance` | `amount` | Ожидаемый результат |
|---|:--:|:--:|:---:|
| BAL-1 (ниже) | 1001 | 1000 | APPROVED `00` |
| BAL-2 (граница) | 1000 | 1000 | APPROVED `00` |
| BAL-3 (выше на 1) | 999 | 1000 | DECLINED `51` |

### 3.4 Диапазоны генератора карт (CMS-7)

ТЗ 05 §3 задаёт диапазоны в рублях; API возвращает копейки.

| Поле | Нижняя граница | Верхняя граница |
|---|:--:|:--:|
| Баланс | 10 000 ₽ = 1 000 000 | 500 000 ₽ = 50 000 000 |
| Дневной лимит | 50 000 ₽ = 5 000 000 | 300 000 ₽ = 30 000 000 |
| Месячный лимит | = дневной × 30: 150 000 000 | = дневной × 30: 900 000 000 |

### 3.5 Пагинация (CMS-4), P2

Предусловие: в БД не менее 25 карт со статусом ≠ `DELETED`; `T` — значение `total` из ответа без параметров.

| ID | Запрос | Ожидаемый результат |
|---|---|---|
| PAG-1 | `GET /api/cards?limit=0` | 400 Bad Request |
| PAG-2 | `GET /api/cards?limit=1&offset=0` | 1 карта, `total` = `T` |
| PAG-3 | `GET /api/cards` (без параметров) | `min(50, T)` карт — значение по умолчанию `limit=50` |
| PAG-4 | `GET /api/cards?limit=10&offset=0`, затем `limit=10&offset=10` | по 10 карт, пересечения PAN между страницами нет |
| PAG-5 | `GET /api/cards?offset={T}` | пустой `cards`, `total` = `T` |

## 4. Decision table — авторизация транзакции (AUTH-3 … AUTH-12)

Условия:
- **C1** — карта найдена в CMS
- **C2** — статус карты `ACTIVE`
- **C3** — срок действия валиден (`expiryDate` не в прошлом)
- **C4** — дневной лимит не превышен
- **C5** — месячный лимит не превышен
- **C6** — баланса достаточно
- **C7** — CMS доступна (и при чтении карты, и при `reserve`)

| | DT-1 | DT-2 | DT-3 | DT-4 | DT-5 | DT-6 | DT-7 | DT-8 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| C1 карта найдена | Н | Д | Д | Д | Д | Д | Д | Д |
| C2 статус ACTIVE | — | Н | Д | Д | Д | Д | Д | Д |
| C3 срок валиден | — | — | Н | Д | Д | Д | Д | Д |
| C4 дневной лимит | — | — | — | Н | Д | Д | Д | Д |
| C5 месячный лимит | — | — | — | — | Н | Д | Д | Д |
| C6 баланс | — | — | — | — | — | Н | Д | Д |
| C7 CMS доступна | Д | Д | Д | Д | Д | Д | Н | Д |
| **Результат** | `14` | `CARD_INACTIVE`/`CARD_BLOCKED`/`54` | `54` | `61` | `61` | `51` | `05` | **APPROVED** `00` |
| Кейсы | AUTH-3-02 | AUTH-4-01, AUTH-5-01, AUTH-6-01 | AUTH-7-01 | AUTH-8-02, NP-3 | AUTH-9-02, NB-3 | AUTH-10-02, BAL-3 | AUTH-11-02, AUTH-11-03 | AUTH-12-01 |

Пояснения:
- **DT-2** — `INACTIVE`→`CARD_INACTIVE`, `BLOCKED`→`CARD_BLOCKED`, `EXPIRED`→`54`; три исхода — три отдельных кейса.
- **DT-7** — `05`/`ISSUER_TIMEOUT` независимо от C1–C6. CMS вызывается дважды (чтение карты и `reserve`), поэтому DT-7 покрывается двумя кейсами: AUTH-11-02 и AUTH-11-03.
- При одновременном нарушении нескольких условий побеждает первое по порядку C1→C6 (кейсы AUTH-12-04…05).

## 5. Тест-кейсы

Во всех кейсах авторизации запрос отправляется напрямую в Authorization (`POST :8083/api/internal/authorize`). «Свежая карта» — карта, созданная через `POST /api/cards` под кейс, с `limit_usage` без записей; нужное состояние готовится по [тест-плану, §4](test-plan.md#4-тестовые-данные). Во всех DECLINED-кейсах дополнительно проверяется, что `availableBalance` и `limit_usage` не изменились.

### 5.4 Попарное тестирование

Таблица решений (§4) и граничные значения (§3) покрывают случаи «нарушено одно условие». Попарные наборы проверяют взаимодействие одновременно варьируемых параметров: каждая пара значений встречается хотя бы раз. Наборы генерируются заново командой `pict <модель>.pict` и дополняются колонками `id` и ожидаемого результата.

#### Модель авторизации — `authorization-decision.pict`, 37 кейсов (PW-AUTH-01…37), P2

Подготовка строки: свежая карта нужного `bin` и `card_status`; запись в `limit_usage` за сегодня с `daily_amount = D = 50 000`; сумма транзакции `A = 100 000`. Классы задаются полями карты:

| Параметр | Значение | Как получить |
|---|---|---|
| `expiry` | `PAST` / `CURRENT_MONTH` / `FUTURE` | `expiry_date` = прошлый / текущий / следующий месяц (MMYY) |
| `daily` | `WITHIN` / `ON_LIMIT` / `OVER` | `dailyLimit` = `D + A + 100 000` / `D + A` / `D + A − 1` |
| `monthly` | `WITHIN` / `ON_LIMIT` / `OVER` | `monthlyLimit` = `M + A + 100 000` / `M + A` / `M + A − 1`, где `M` — сумма `daily_amount` за месяц |
| `balance` | `WITHIN` / `EQUAL` / `OVER` | `availableBalance` = `A + 100 000` / `A` / `A − 1` |
| `bin_lookup` | `OK` / `HTTP_5XX` / `UNAVAILABLE` | сервис работает / заглушка отвечает 503 / контейнер остановлен |

Ограничения модели:
- Если отказ наступает на раннем шаге (статус не `ACTIVE`, срок в прошлом, превышен дневной или месячный лимит), последующие параметры фиксируются в `WITHIN`. Они не влияют на ответ, и без ограничения пары граничных значений тратились бы на строки, где граница не проверяется.
- `EXPIRED` сочетается только с `PAST`: при будущем сроке ответ тот же (`54`), строка не добавляет информации.

Ожидаемый результат (колонки `expected_*`) выводится по порядку проверок §4: первое нарушенное условие определяет код. `bin` и `bin_lookup` на решение влиять не должны: если строки отличаются только этими параметрами, а результат разный — это дефект fallback (AUTH-2). Пары с `DT-1` (карта не найдена) и `DT-7` (CMS недоступна) в модель не входят: при них остальные параметры не определены, они проверяются отдельными кейсами.

#### Модель создания карты — `card-creation.pict`, 20 кейсов (PW-CMS-01…20), P2

| Параметр | Значения | Расшифровка |
|---|---|---|
| `bin` | `400000…400004` | все BIN стенда |
| `cardholder_name` | `MIN_LENGTH` / `NORMAL_LENGTH` / `MAX_LENGTH` | `"A"` / `"IVAN IVANOV"` / 255 символов `A` (`VARCHAR(255)`, ТЗ 05 §6) |
| `currency_code` | `643` / `840` / `978` | RUB / USD / EUR (ISO 4217) |
| `daily_limit` | `1` / `15000000` / `500000000` | минимальный положительный / значение по умолчанию из ТЗ / заведомо большой |
| `monthly_limit` | `1000000` / `300000000` / `3000000000` | малый / по умолчанию / большой |
| `initial_balance` | `0` / `100000000` / `1000000000` | пустой / по умолчанию / большой |

Ограничение исключает только комбинацию большого дневного лимита с минимальным месячным (в 500 раз меньше): ТЗ не требует `monthlyLimit ≥ dailyLimit`, но такая карта нереалистична. Ожидаемый результат одинаков для всех строк: карта создана, `status=ACTIVE`, PAN проходит Луна и начинается с `bin`, остальные поля равны входным.
