# Тест-план — Authorization и Card Management

## 1. Объекты тестирования

| Объект | Порт | Версия |
|---|:-:|---|
| Authorization | 8083 | ветка `practice-2` |
| Card Management | 8081 | ветка `practice-2` |
| Bin Lookup (зависимость) | 8096 | ветка `practice-2` |
| PostgreSQL, RabbitMQ (зависимости) | 5432, 5672 | из `docker-compose.yaml` |

Остальные сервисы СМП участвуют только как среда: Authorization вызывается через Switch, но Switch не тестируется.

### 2.2. Что не тестируем

| Что | Основание |
|---|---|
| PIN/CVV-проверка, 3-D Secure, кэш карт | Бонусные функции ТЗ 04 вне обязательного объёма; из бонусных проверяются только reversal (используется Switch) и outbox |
| Gateway, Switch, Logger, симуляторы, Dashboard | Вне объектов практики; проверяются на сквозном уровне позже |

## 3. Окружение

| Параметр | Значение |
|---|---|
| Стенд | локальный, `docker compose up -d`: 11 сервисов + PostgreSQL + RabbitMQ |
| Входная точка | Gateway `:8080`; Authorization и Card Management также напрямую (`:8083`, `:8081`) |
| Порты | 3000, 5432, 5672, 8080–8097, 15672 должны быть свободны |
| Ресурсы | Docker, не менее 8 ГБ RAM |
| Инструменты | curl/Postman, PICT, psql, RabbitMQ Management UI (`:15672`) |
| Имитация отказов | `docker stop` нужного контейнера (CMS, bin-lookup, RabbitMQ), затем запуск обратно |
| Имитация 5xx bin-lookup | вместо `bin-lookup` поднимается заглушка (WireMock) с тем же именем хоста и портом `8096`, отвечающая 503 на `GET /api/bin/{bin}`; число обращений берётся из журнала заглушки |
| Отказ CMS на `reserve` (AUTH-11-03) | та же заглушка вместо CMS: `GET /api/cards/{pan}` проксируется в реальную CMS, `POST /api/cards/{pan}/reserve` отвечает таймаутом |

## 4. Тестовые данные

- Карта создаётся через `POST /api/cards`; `status`, `dailyLimit`, `monthlyLimit`, `availableBalance` выставляются через `PATCH /api/cards/{pan}`.
- `expiryDate` через API не меняется (ТЗ 05 §2: `POST` задаёт +3 года, `PATCH` поле не принимает), поэтому для AUTH-7 и PICT-строк с `expiry` ≠ `FUTURE` срок выставляется в БД: `UPDATE cards SET expiry_date = '<MMYY>' WHERE pan = '<pan>';`.
- Генератор выдаёт `INACTIVE` и `BLOCKED` лишь в 3 % и 2 % случаев, поэтому нужные статусы выставляются явно через `PATCH`.
- Для границ лимитов используется свежая карта на каждый кейс; «предыстория трат» создаётся прямой записью в `limit_usage` (`card_id`, `usage_date`, `daily_amount`, `monthly_amount`) — так точнее, чем серия авторизаций.
- Суммы — в копейках; BIN — из `400000…400004`.
- После прогона карты не переиспользуются: следующий прогон создаёт их заново.

## 5. Критерии входа

1. Все контейнеры `Up (healthy)` (`docker compose ps`).
2. `./scripts/smoke-test.sh` завершается успешно.
3. Карточный пул создан (`POST /api/cards/generate`, не менее 20 карт).
4. Кейсы на проверяемый блок спроектированы в test-design.

Если п. 1 или 2 не выполнен, результаты прогона не учитываются: проверяется стенд, а не логика.

Исключение из п. 3: CMS-1-02 (пустая БД) выполняется первым, до генерации пула.

## 6. Критерии выхода

| # | Критерий | Значение |
|:-:|---|:-:|
| 1 | Требования реестра (кроме бонусных) покрыты кейсами | 100 % |
| 2 | Кейсы приоритета P1 выполнены и пройдены | 100 % |
| 3 | Кейсы приоритета P2 пройдены | ≥ 90 % |
| 4 | Кейсы приоритета P3 | выполняются по возможности, на выход не влияют |
| 5 | Каждое условие отказа из ТЗ 04 воспроизведено минимум одним кейсом: `responseCode` `14`; `54` по статусу и `54` по сроку; `61` по дневному и `61` по месячному лимиту; `51`; `05` + `ISSUER_TIMEOUT`; `declineReason` `CARD_INACTIVE` и `CARD_BLOCKED` | 100 % условий |
| 6 | Оба попарных набора выполнены целиком (37 + 20 строк) | 100 % строк |
| 7 | Открытые дефекты Critical и Major | 0 (или обоснованная отсрочка) |
| 8 | Каждое падение оформлено баг-репортом со ссылкой на требование и ID кейса; кейсы, зависящие от открытых вопросов Q1–Q4 (test-design §1.1), — вопросом куратору | 100 % |
| 9 | Нестабильные кейсы (разный результат при повторе без изменений) | 0 без объяснения причины |

Покрытие ветвлений и метрики нагрузки в этой практике не измеряются: они относятся к unit-уровню и нагрузочному smoke (практики 4 и 6).

## 7. Критерии приостановки и возобновления

**Приостановка** прогона, если:
- не проходит smoke или контейнер не поднимается;
- недоступна БД или Card Management (кроме кейсов, где это и проверяется);
- три и более кейса подряд упали по одной и той же причине;
- обнаружено, что состояние данных повреждено (например, `limit_usage` содержит суммы от прошлых прогонов);
- изменилось ТЗ, и ожидаемые результаты устарели.

**Возобновление**, когда:
1. причина устранена и записана в отчёт;
2. стенд перезапущен с чистой БД;
3. smoke пройден;
4. кейсы, упавшие до остановки, перепрогнаны целиком, а затронутые изменением ТЗ — переписаны.

## 8. Риски плана

| Риск | Реакция |
|---|---|
| Нестабильный стенд (Docker, нехватка ресурсов) | Пересборка образов, фиксация окружения в отчёте |
| Сложно воспроизвести гонку | Параллельные запросы, повтор не менее 5 раз |
| Остановки сервисов влияют на соседние кейсы | Кейсы с имитацией отказов — отдельным прогоном после основных |
| Расхождение ТЗ и реализации превращается в спор «дефект или уточнение» | Фиксировать расхождение в баг-репорте со ссылкой на пункт ТЗ |
